# UI 接口拆分 Phase 1

## 目标

当前仓库的 CLI 与 Textual TUI 直接依赖具体实现，后续如果继续开发新的用户界面，界面层会继续和配置、模板持久化、云端同步逻辑强耦合。这个阶段先补齐共享接口层，并保持现有功能可继续运行。

本阶段最初没有直接实现新的 `pysier` 界面，因为仓库内不存在对应线索。现已由用户澄清：这里的目标界面实际是 **`PySide6`**。因此 Phase 1 的接口层输出将继续作为后续 `PySide6` 界面的共享基础。

## 子任务拆分

1. **现状调研**：定位现有 TUI / CLI / 配置 / 模板 / 同步之间的耦合点。
2. **接口建模**：定义共享的 Pydantic 数据模型与 Protocol 接口。
3. **模板仓储抽离**：把模板 JSON 读写从交互逻辑中分离出去。
4. **配置与同步适配**：让 `ConfigManager` 和 `RemoteSyncService` 实现新的接口约束。
5. **TUI 注入改造**：让 `TemplateManagerApp` 依赖接口而不是直接绑死具体实现。
6. **CLI 复用抽象**：让 `MessageManager` 复用共享模板仓储，减少重复逻辑。
7. **测试补齐**：在单独的 `tests/` 目录验证新接口和适配器。
8. **下一阶段 TODO**：接口层稳定后，再拆出后续 UI 开发任务。

### 1. TUI 架构调研子代理

**为什么这样做**

先交给独立子代理梳理 `tui_app.py`、`main.py`、`config_manager.py`、`remote_sync_service.py` 之间的耦合关系，可以快速找到真正需要抽象的边界，避免主线程在不了解全局结构时直接改代码。

**结论**

- `MessageManager` 同时承担模板持久化和 CLI 交互。

**优点**

- 快速确认了最小接口范围。
- 提前发现了启动同步导致的依赖注入陷阱。

**缺点**

**后续建议**

- 本阶段先抽象配置、模板仓储、同步服务。
- 暂不提前抽象 `AwinRPA`，等后续真正进入第二套 UI 时再定边界。

## 当前设计决策

### 决策 1：本阶段只抽象“界面依赖的共享服务接口”

**为什么这样写**

真正需要先稳定的是界面会消费的数据和服务边界，而不是界面组件本身。也就是说，先统一“设置怎么读写”“模板怎么读写”“同步怎么拉推”，后续不管是 Textual、CLI 还是新的 UI，都可以共用这一层。

**优点**

- 抽象层级明确，直接服务于后续 UI 开发。
- 对现有功能侵入较小，迁移风险可控。

**缺点**

- 不能一次性解决所有架构耦合问题。
- `AwinRPA` 这样的重型对象仍然留在下一阶段处理。

**后续建议**

- Phase 2 再根据新 UI 的真实交互流程决定是否补充 `RPA` 接口。

### 决策 2：使用 Pydantic 承载共享数据模型

**为什么这样写**

这是为了满足你的 Python 规范，并把原本分散在字典和属性里的约束集中起来，例如通知渠道合法值、默认配置、模板结构等。

**优点**

- 统一数据校验。
- 便于测试和后续序列化。
- 后续给第二套 UI 复用时更稳定。

**缺点**

- 需要新增依赖并改造现有数据读写逻辑。

**后续建议**

- 如果后续配置继续扩张，可以再考虑把环境变量配置也并入 Pydantic Settings。

### 决策 3：保留 TUI 启动时的“两阶段同步”

**为什么这样写**

当前 TUI 启动顺序是：先读取本地配置拿到同步地址，再从云端拉取，再重新加载本地配置。这虽然不是最优结构，但当前行为已经存在，直接删除会引入不易察觉的兼容性问题。

**优点**

- 行为保持一致。
- 可以在不重写整体启动流程的前提下完成接口落地。

**缺点**

- 依赖注入会比普通构造函数更复杂，需要使用工厂而不是单例对象。

**后续建议**

- 未来可以把远端拉取改成“返回结构化数据”而不是“直接写文件”，进一步消除两阶段初始化。

### Step 3：抽离模板 JSON 仓储

**涉及文件**

- `json_template_repository.py`
- `main.py`

**为什么这样写**

原来的 `MessageManager` 同时负责“模板文件读写”和“CLI 交互”，这让 TUI 和未来新界面都不得不绕回 CLI 逻辑。本次新增 `JsonTemplateRepository` 作为单独的数据访问层，并让 `MessageManager` 复用它，只保留交互职责。

**优点**

- 模板持久化逻辑不再散落在多个 UI 文件里。
- CLI 和 TUI 共享同一份模板存储实现。
- 为未来 GUI / `PySide6` UI 提供了可直接复用的模板接口。

**缺点**

- 现在仓储仍然是文件级全量读写，还不是更细粒度的 repository/service 拆分。

**后续建议**

- 如果后续要支持多用户、多环境或者远端模板版本控制，可以在这一层之上再加应用服务。

### Step 4：让配置与同步服务对齐接口

**涉及文件**

- `config_manager.py`
- `remote_sync_service.py`

**为什么这样写**

`ConfigManager` 现在内部改为使用 `AppSettings`，并对外暴露稳定的配置属性、快照与同步 payload。`RemoteSyncService` 则新增结构化的 `pull_configs()`，把远端返回值解析成模型，而不再要求调用者只能通过“直接写文件”这种方式使用它。

**优点**

- 配置合法性检查集中到了模型层。
- 同步服务开始具备“返回结构化数据”的能力，后续更容易接 GUI。
- 同时保留了旧的 `pull_and_apply()` 兼容入口，降低了迁移风险。

**缺点**

- 目前仍保留了旧兼容方法，短期内会同时存在新旧两种调用路径。

**后续建议**

- 等第二套 UI 真正接入后，可以逐步删掉只为兼容保留的旧文件写入路径。

### Step 5：TUI 切换到接口驱动的依赖注入

**涉及文件**

- `tui_app.py`

**为什么这样写**

`TemplateManagerApp` 现在不再直接依赖 `MessageManager` 读取模板，而是接收模板仓储、配置仓储工厂、同步服务工厂和 UID 提供器。这里特意保留了“两阶段初始化”：先拿本地配置创建同步服务，拉远端配置后再重新构造配置仓储，避免把启动同步行为改坏。

**优点**

- 现有 TUI 已经开始依赖接口，而不是硬编码到具体实现。
- 后续写新的 UI 时，可以直接注入另一套实现。
- 保住了现有远端同步启动行为。

**缺点**

- 构造函数比以前复杂，理解成本更高。
- 由于现有启动行为需要兼容，仍然使用了工厂而不是最简单的单实例注入。

**后续建议**

- Phase 2 可以把启动同步进一步改成“服务返回数据，应用层决定如何落盘和刷新状态”，从而简化构造过程。

## 本批任务实现记录（PySide6）

### Step 8：补充共享 UI 状态模型与应用服务接口

**涉及文件**

- `app_interfaces.py`

**为什么这样写**

这一步先把 `TemplatePanelViewModel`、`SettingsViewModel`、`BrowserConnectionViewModel`、`ExecutionStateViewModel`、`AppRuntimeStateViewModel` 等运行态模型补齐，同时新增 `RpaRunnerProtocol` 和 `ApplicationServiceProtocol`。这样后续不管是 Textual TUI 还是 PySide6，都先围绕同一套接口和状态模型协作，再去写具体实现。

**优点**

- 满足“先定义接口再写实现”的规范。
- 让 PySide6 界面不需要直接理解底层配置文件和浏览器对象。
- 测试时可以直接伪造服务和状态模型，降低 UI 测试复杂度。

**缺点**

- `app_interfaces.py` 承担的职责更多，后续如果继续扩张，可能需要拆分为更细的 contracts 模块。

**后续建议**

- 如果后面 ViewModel 继续增长，可以把“领域接口”和“界面状态模型”拆成两个文件。

### Step 9：抽离共享应用服务

**涉及文件**

- `awin_application_service.py`
- `main.py`

**为什么这样写**

这里新增了 `AwinApplicationService`，统一承接模板加载、配置同步、模板 CRUD、通知设置更新、浏览器连接、记录重置和执行流程。`main.py` 里的 `AwinRPA` 也补了公开方法，避免界面层再去访问 `_clicked_publisher_ids` 这样的内部状态。

**关键设计**

- 服务方法保持**同步**，不内置 Textual 或 Qt 的线程模型。
- 线程调度仍由 UI 自己负责：TUI 用 `@work(thread=True)`，PySide6 用 `QThread`。

**为什么这样写**

这是对方案校验反馈的直接响应。如果把线程也塞进服务里，会让服务绑死到某个 UI 框架，后续另一个界面就难以复用。

**优点**

- 服务边界清晰，可同时服务 TUI 和 PySide6。
- 执行逻辑、连接逻辑、重置逻辑终于不再散落在各个界面里。
- `AwinRPA` 的内部集合不再暴露给 UI。

**缺点**

- 服务现在是有状态对象，持有浏览器连接实例，天然不适合多个 UI 会话共享。

**后续建议**

- 如果后续需要多窗口 / 多会话，应该再往下抽浏览器 session manager。

### Step 10：让现有 TUI 浏览器相关路径切到服务层

本批任务不仅需要给 PySide6 一个新的壳层，也需要把“抽离 RPA 应用服务”做实。所以这里没有只写新 UI，而是把现有 TUI 的启动初始化、浏览器连接、记录重置和执行流程改为通过 `AwinApplicationService` 调用。

**优点**

- 降低后续继续迁移 TUI 其余逻辑的风险。

**缺点**

- TUI 的模板编辑和设置编辑目前仍然保留一部分界面本地状态，需要和共享服务协同维护。

**后续建议**

- 下一步可以继续把 TUI 的模板编辑和设置保存入口也彻底收敛到服务方法，减少双向状态同步。

### Step 11：实现首版 PySide6 UI 壳层

**涉及文件**

- `pyside6_app.py`
- `pyproject.toml`

**为什么这样写**

这里实现的是“薄壳式” PySide6 主窗口：界面负责展示模板、配置和日志，按钮只负责分发事件；真正的业务逻辑统一调用共享应用服务。浏览器连接和执行流程使用 `QThread` 包装，以适配 Qt 的线程模型。

**实现范围**

- 模板列表查看、选择、编辑、保存、删除、激活
- 发送数量编辑
- 通知渠道与飞书 Webhook 编辑
- 启动时 bootstrap 远端同步
- 手动重新同步
- 浏览器连接
- 重置已点击记录
- 开始 / 停止执行
- 日志输出

**优点**

- PySide6 已经具备可运行的首版 GUI 外壳。
- 业务没有复制粘贴，而是复用共享服务。
- 线程模型和 UI 更新职责边界明确。

**缺点**

- 当前版本仍然是手工刷新控件，不是 Qt 更原生的 Model/View 绑定。
- 启动时 bootstrap 仍然在主线程完成，后续可以再异步化。

**后续建议**

- 如果界面规模继续扩大，再考虑引入更明确的 controller / presenter 层。

### Step 12：补 PySide6 与服务层测试

**涉及文件**

- `tests/test_awin_application_service.py`
- `tests/test_pyside6_app.py`
- `tests/conftest.py`
- `pyproject.toml`

**为什么这样写**

这一步把“接口层测试”推进到了“应用服务 + GUI 壳层测试”。服务层测试覆盖模板删除后的激活索引修复、连接/执行/重置主流程；PySide6 测试覆盖窗口初始化、后台连接按钮和模板新增按钮。

**优点**

- 共享服务和 PySide6 壳层都有了直接回归保护。
- 测试运行在独立 `tests/` 目录，符合当前规范。
- 通过 `QT_QPA_PLATFORM=offscreen` 兼容无界面环境。

**缺点**

- 目前的 PySide6 测试仍然是轻量级集成测试，还没有覆盖更多复杂交互。

**后续建议**

- 后续可以继续补执行停止、模板激活、设置校验失败等 GUI 场景。

## 对方案校验反馈的响应

### 反馈 1：服务不应内置线程模型

**响应**

已采纳。`AwinApplicationService` 的方法全部保持同步，线程调度由外层 UI 自己处理：

- Textual TUI：`@work(thread=True)`
- PySide6：`QThread`

### 反馈 2：PySide6 测试需要补 `pytest-qt`

**响应**

已采纳。`pyproject.toml` 已新增 `PySide6` 与 `pytest-qt`，并补了 `offscreen` 运行配置。

### 反馈 3：避免一次性重写整套 TUI

**响应**

部分采纳。本批没有把 TUI 全量重构到服务层，而是优先迁移了最耦合、最关键的浏览器连接 / 重置 / 执行路径，既完成服务抽离目标，也尽量降低对现有稳定 TUI 的破坏风险。
